## Context
This uses Functions because it writes across two accounts (the child's data lands in the parent's tree). It must be atomic and impossible to replay.

## Scope
- Callable `claimLinkToken(token)` (a signed-in, non-anonymous parent): in a transaction, validate the token is unexpired and unclaimed, generate a 6-digit code (`crypto.randomInt`), set `claimedBy`/`code`/`status=claimed`, and return the code + child model. Uses the M7-02 rate limit and consumes the App Check token.
- Parent "Confirm link" screen: the 6-digit code, an editable device name, a note that the child can unlink anytime, then waiting for the child to tap Allow.
- Kids "Consent" screen: the same code, the list of what the parent can do (prototype `consentList`), and "Allow and link" → callable `approveLink(token, approve)`. The caller must be the token's `childUid`. In a transaction it creates `users/{parent}/devices/{id}` with `childUid`, name and model, marks the token `used` (or `declined`), and returns parent uid + device id for the child to store locally.
- The parent sees the success → Remote device screen, toast "Phone linked". Also handle deny, timeout and code mismatch.

## Acceptance criteria
- [ ] An emulator integration test covers the full handshake, plus: replay of a used token, claim of an expired token, approve by the wrong uid, and two parents racing to claim one token.
- [ ] A two-device manual test on dev, with a screen recording in the PR.
