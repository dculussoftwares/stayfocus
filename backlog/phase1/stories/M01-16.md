## Context
Unit and screenshot tests don't prove that screens, navigation, permissions and the blocking overlay work on a real Android system. This story sets up two levels of on-device testing that later stories extend.

## Scope
- **Instrumented tests (Compose UI / AndroidX Test)**
  - Gradle Managed Devices: `pixel6Api26` and `pixel6Api36` using ATD (Automated Test Device) images, grouped as `ciDevices`. `./gradlew ciDevicesGroupDebugAndroidTest` runs them headless.
  - A shared test harness in `:core:testing` (Hilt test runner, `HiltTestApplication`, fake repositories, `TestClock`).
  - First tests: the app launches, the 4-tab navigation and back behaviour work (from M1-09), and both apps start.
  - CI job `instrumented-tests` in `ci.yml` on PRs (ubuntu runner with KVM enabled, AVD cache); test reports and failure screenshots uploaded; included in `ci-pass`.
- **End-to-end flows (Maestro)**
  - `e2e/flows/` with Maestro YAML flows and a `README` on running them locally (`maestro test e2e/flows`).
  - First flows: `smoke/app_launch.yaml` (both apps) and `smoke/navigation_tabs.yaml`.
  - **PR gate:** an `e2e-smoke` job in `ci.yml` runs the smoke flows (`e2e/flows/smoke/**`, kept under ~5 minutes) on every PR, and `ci-pass` needs it, so a broken user journey blocks the merge.
  - Workflow `e2e.yml` (full suite): on push to `main`, nightly and on manual dispatch. Builds debug APKs, starts an API 36 emulator (`reactivecircus/android-emulator-runner`, SHA-pinned), runs every flow, and uploads screenshots, videos and the JUnit report. Failures on `main` open/update a single tracking issue.
  - Flows use test tags / content descriptions, not coordinates; permissions are granted with `adb shell appops`/`pm grant` in a setup flow where Settings screens would otherwise be needed.
- **Convention for later stories:** a story that adds or changes a user journey adds or extends a Maestro flow. The key journeys to cover as they land are onboarding + permissions (M5), create each block type (M4), Take a break + block screen (M2), account sign-in (M6, against the Auth emulator), and linking (M7, two emulators where feasible, otherwise a documented manual check).

## Acceptance criteria
- [ ] `instrumented-tests` runs on PRs in under ~15 minutes and fails when a navigation test fails.
- [ ] A PR that breaks a smoke flow fails `e2e-smoke` and therefore `ci-pass`.
- [ ] `e2e.yml` runs the full flow suite on an emulator and publishes video and screenshots.
- [ ] The Definition of done in the plan references the E2E convention.
