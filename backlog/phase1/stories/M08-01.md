## Context
No server is needed: the child already runs a 24/7 foreground service (M7-08) and has battery optimisation turned off, so a realtime Firestore listener delivers commands within seconds. The rules (M7-03) are the security boundary.

## Scope
- Command types: `BLOCK_APP`, `UNBLOCK_APP`, `START_FOCUS{mins}`, `STOP_FOCUS`, `APPROVE_REQUEST{reqId, mins}`, `DENY_REQUEST{reqId}`, `SYNC_BLOCKS`, `REMIND_PERMISSION{permission}`.
- Parent `CommandSender` writes `commands/{id}` (status `pending`, `createdAt` = server timestamp).
- Child `CommandListener` in `MonitoringService`: a snapshot listener on `status == pending` → a `CommandExecutor` registry (handlers plug in from M8-03/M8-05) → set `done`/`failed` + `ackAt`. Execution is idempotent by command id. Commands older than 24 h are marked `expired`, not run.
- The listener restarts on service restart and boot, and re-attaches after network loss (Firestore handles offline; verify).
- Parent UI helper: pending until acked; "Phone is offline, it'll apply when it's back" after 10 s without an ack.

## Acceptance criteria
- [ ] Unit tests for executor idempotency and expiry.
- [ ] A dev manual test reports command latency (p50/p95 over 20 commands, screen on and off) in the PR.

## Out of scope
FCM wake-ups for the child. Add them later only if the latency test shows the listener isn't enough.
