## Context
Rules are the main security boundary (plan §9): most flows are direct client writes. Deny by default; every allowed write validates its fields.

## Scope
- Finalise the data model in plan §7 (update the doc). `firestore.rules`, deny by default, with helper functions (`isParent(uid)`, `isChildOf(deviceDoc)`, `onlyChanges([...])`, type and size validators):
  - **Parent** (`request.auth.uid == uid`, non-anonymous): read `users/{uid}/**`; create/update its own profile doc `users/{uid}` (`displayName`, `email`, `createdAt` only); write `blocks`, `commands` (create only, a fixed schema), the request decision fields (`status`, `decidedAt`), alert `dismissed`, and its own `fcmTokens`. It **can't** create or delete device docs (Functions only).
  - **Child** (`request.auth.uid == device.childUid`): read its own device doc, `blocks` and `commands`. Update only its status fields (`battery`, `charging`, `currentApp`, `online`, `lastSeen`) and command `status`/`ackAt`. Create `requests`, `alerts`, `usage/{date}` and `apps` with schema and size checks. It can't read other devices or the parent's profile.
  - `linkTokens/{token}`: create only by a signed-in child with `childUid == auth.uid`, `expiresAt ≤ now + 5 min`, no `claimedBy`. Read only by that child (to see the claim). No client update or delete; claiming goes through Functions.
  - `rateLimits/**`, and anything else unlisted: no client access.
- Rules unit tests with `@firebase/rules-unit-testing` running in CI (`firebase emulators:exec`).

## Acceptance criteria
- [ ] ≥ 40 allow/deny test cases, including cross-parent access, a child writing forbidden fields, a parent creating a device doc, oversized payloads and an expired token.
- [ ] Plan §7 and §9 are updated to match the rules.
