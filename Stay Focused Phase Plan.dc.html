STAY FOCUSED · ANDROID · OPEN SOURCE · DRAFT v1

Product plan, phase by phase

A free, open-source app blocker for Android. You sign in with an account and can link and control your other devices from your phone by scanning a QR code. This plan covers what I understood from the reference screenshots, the scope of each phase, the Phase 1 screens, and the questions we still need to settle before I build the Phase 1 prototype.

1. Reference app teardown

Dashboard
Today's screen time and launches, Take a Break presets, the current mode, 6 stacked quick-action cards, profiles and templates. Too much is packed into one screen, so users have trouble telling which items are features and which are status.
Modes
Normal, Lock (password) and Strict (deactivation method). Each mode shows 1 to 3 locks for how strict it is, and this works well as a mental model.
Analytics
Day stepper, 5 metric tabs, an hourly bar chart with an average line, and per-app usage bars with overflow menus.
All Apps
Search, Pinned sort, and a lock toggle on every app with time spent and launches. When an app is blocked, its row expands to show the rule.
Profile wizard
Pick a condition from 7+ types, then a sub-type such as daily or hourly, then the rules: what to block (launch or notification), days, interval and threshold picker. Powerful, but the user has to understand the jargon before they can start.
What we drop
Ads, the trial pill, Upgrade badges, and the 18+ upsell placed among the quick actions. The app is free, so every screen can stay focused on the job.

2. UX principles

  1. Plain words for each block type. We say "Limit time", "Block during hours" and "Block now". We avoid "Blocking Condition".
  2. Templates first, custom second. Most people start by tapping a template, then adjust it.
  3. Status and actions are separate. The dashboard shows what is happening. Settings live in their own tab.
  4. Every device looks the same. A linked device uses the same dashboard as this phone, scoped to that device. Nothing new to learn.
  5. Permissions are explained just before they are needed. One screen per permission, and each one says why.

3. Phases

PHASE 1 · v1.0
Block, limit, link
First Play Store release
Accounts: Google sign-in and email + password (Firebase Auth), with forgot-password.
Device linking: a parent links a child's phone by scanning the QR code shown on the child's phone. The child's phone needs no account. Includes a device list, unlinking, and tamper alerts.
Remote controls: view usage, block or unblock apps, start or stop a focus session, approve unlock requests, see live status (online, battery, current app).
Blocking: app blocker, usage limits (daily and hourly), Use, then rest (each time you open an app you get X minutes, then it's blocked for Y minutes), schedules (time intervals), Quick Block and Take a Break.
AI block builder: describe a block in your own words, e.g. "Instagram 10 min, then lock 1 hour". The AI fills in the block form, and you review it before it turns on.
Analytics: screen time, launches, unlocks, per-app detail, day and week.
Normal mode only. Instead of tamper protection, the parent gets tamper alerts.
PHASE 2
Commitment
Lock and Strict modes (Device Admin, uninstall protection), website blocker, Reels/Shorts blocker, notification blocking, launch-count and wait-timer limits. New remote controls: switch modes, edit profiles, lock now.
PHASE 3
Focus & study
Pomodoro and study timer with automatic blocking, focus sounds, goal-based unlocks, keyword blocker, adult content filter, Strict Alarm.
PHASE 4
Groups & context
Admin and team/school groups, location blocking, digital detox schedules, home-screen widgets, and optional monetization.

5. Linking flow (draft)

  1. On the device to be controlled: install the app, then Devices → Link to another phone. A QR code appears, valid for 5 minutes.
  2. On the controller phone: Devices → Add device → scan the code.
  3. Both screens show a matching confirmation code. The child's phone shows exactly what the parent will be able to do and asks for consent.
  4. The device appears in the controller's list. A permanent notification on the controlled device says "Managed by Alex's phone".
  5. When an app is blocked, the controlled device can tap Ask for more time. The controller gets a push notification with Approve 15 / 30 / 60 min or Deny.
Play Store rule. Linking is allowed for parent → child only. Google prohibits monitoring another adult, such as a partner, even if they consent. See section 8.

6. Technical notes

  • Kotlin + Jetpack Compose. UsageStatsManager for analytics, an AccessibilityService and overlay for blocking.
  • Firebase Auth, Firestore for device state and commands, and FCM to wake the controlled device for remote commands.
  • Open source: forks bring their own google-services.json. Blocking also works offline, without an account.
  • AI block builder: Gemini through Firebase AI Logic, which fits the Firebase stack and has no server to run. Answers come back in a strict JSON format that maps to the 4 block types. The AI only receives the sentence the user typed, never their usage data. If AI is unavailable or the user is offline, the app falls back to a simple rule-based reader on the phone. The AI never turns a block on by itself. Play's AI-generated content policy applies lightly here because the output is a settings form, not content. Still mention AI in the listing and Data safety form, and let users report a bad result.
  • Battery optimisation must be turned off on the controlled device, or remote commands arrive late on some OEMs (Xiaomi, Oppo, Vivo).

7. Decisions (agreed)

  1. Parent → child only. One phone controls, the other is controlled. A device can't be both. Admin/team linking moves to Phase 4.
  2. The child device doesn't need an account. It links to the parent's account through the QR code.
  3. Child shows, parent scans. Only the child's phone shows a QR code, and only the parent's phone can scan it. Both then confirm a 6-digit code.
  4. The child can unlink anytime. The parent gets a notification when they do.
  5. Tamper alerts. The parent is told when a permission is turned off or the app is uninstalled.
  6. Tabs: Home · Block · Devices · Insights.
  7. Free with no ads for now. Monetization comes later.

8. Play Store compliance: Phase 1

These are the items that most often block an app blocker or parental-control app at review. Each one is built into the Phase 1 design. The ones that need code or Play Console work are marked so they can be planned early.

TIMELINE BLOCKER
Closed test: 12 testers for 14 days
New personal developer accounts (created after 13 Nov 2023) must run a closed test with at least 12 testers, opted in for 14 days in a row, before they can apply for production access. Plan about 3 weeks between the build being finished and the public launch. Organization accounts with a D-U-N-S number are exempt. Start recruiting testers during development.
Accessibility API
Do not set isAccessibilityTool; that flag is only for disability tools. Show a separate in-app disclosure screen right before sending the user to Settings. It says what data is read (the app in the foreground) and how it's used (blocking only, kept on the phone), and needs a clear "Agree" tap. Fill in the Play Console declaration, record the demo video, and mention it in the store listing.
IN PROTOTYPE · PLAY CONSOLE
Monitoring (stalkerware policy)
Sending a child's usage, current app and battery to the parent counts as monitoring. It requires: parent → child only (never adults), the IsMonitoringTool flag in the manifest, a persistent notification with a unique icon whenever it runs, monitoring described in the store listing, and no hidden or "spy" wording.
IN PROTOTYPE · MANIFEST · LISTING
App list without QUERY_ALL_PACKAGES
Build the app picker with a <queries> intent filter for launcher apps (MAIN/LAUNCHER). That covers every app the user can open and avoids a restricted permission and its declaration.
CODE
Foreground service type
The child's phone needs a persistent service for sync and its notification. Declare foregroundServiceType="specialUse" with a written use-case property and complete the FGS declaration in Play Console. The parent's phone only needs WorkManager and FCM, with no foreground service.
MANIFEST · PLAY CONSOLE
Target API 36
Since 31 Aug 2026, new apps and updates must target Android 16 (API 36). Set targetSdk = 36 from day one and test the blocking overlay and usage access on Android 16.
CODE
Account deletion
Accounts can be created, so the app needs a "Delete account" option in-app and a web page for deletion requests, linked in the Data safety form. Deleting the account must remove the Firestore data and the linked child devices too.
IN PROTOTYPE · WEB PAGE
Privacy policy & Data safety
A hosted privacy policy URL, linked in-app and in the listing. The Data safety form declares app activity, device IDs and app info collected from the child's phone, encrypted in transit, with no sharing or ads.
WEB PAGE · PLAY CONSOLE
Usage access & overlay
PACKAGE_USAGE_STATS and SYSTEM_ALERT_WINDOW are special-access permissions the user grants in Settings. Explain each one in-app first (one screen per permission) and never make the app unusable if one is denied.
IN PROTOTYPE
DECIDED
Two apps: Stay Focused + Stay Focused Kids
Google only allows monitoring in apps "exclusively designed and marketed" for parents or enterprise. Stay Focused is mainly a self-control app, so putting monitoring in the same APK risks a rejection that is hard to argue. Recommendation: ship the child side as a small companion app, "Stay Focused Kids". It carries the IsMonitoringTool flag, the persistent notification and the Accessibility declaration. The main app stays a self-control and parent app, with lighter declarations. Both are built from the same open-source repo as two Gradle modules that share the blocking engine.
Phase 2 heads-up: the Accessibility API can't be used to stop someone uninstalling or disabling an app, unless it's authorized by a parent in a parental control app. Self-imposed Strict mode therefore needs Device Admin and its own disclosure, not Accessibility. We'll design that in Phase 2.
